So, is there any way we can compute what the actual bbp is prior to being put into 32 bbp memory space? Yes. The way to avoid the decoded `32 bpp` surface is to compute from the encoded file data, not from the in-memory `CGImage`. In practice: - JPEG: use the file’s sample precision and component count. - Typical RGB JPEG = `8 bits/component * 3 components = 24 bpp` - Typical CMYK JPEG = `8 * 4 = 32 bpp` - PNG: use IHDR `bit depth * channel count`. - RGB PNG = `8 * 3 = 24 bpp` - RGBA PNG = `8 * 4 = 32 bpp` - Indexed PNG = `bit depth * 1`, with palette size tracked separately in `colors` - GIF: indexed, so depth comes from the indexed pixel depth, not an RGBA decode target. So yes, there is a way to compute the “real” file bpp before it gets expanded into a 32 bpp renderable bitmap. That’s exactly why relying on `CGImage.bitsPerPixel` can be misleading for JPEGs: the decoder may hand you a 32 bpp surface even though the file itself is 24 bpp. That’s also the distinction we just fixed in [PictureDataUtilities.swift](SwiftTag/Shared/Utilities/PictureDataUtilities.swift): prefer file-level metadata/parsing first, and only fall back to the decoded image when we have no better source.
